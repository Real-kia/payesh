# Package 08 handoff — CPU Controls

Status: Checkpoint A implemented; package 08 is not accepted. No real
CPU-load test has been run — this macOS host has no cgroupfs at all, so
kernel enforcement of any written quota is unverified.

## Baseline and files

Builds on package-06's module framework (`modules.Manager.DeactivateHooks`)
and the package-05/06 SQLite store. New package: `internal/cpucontrol/`
(quota math, cgroup v2 file adapter, process-identity verification, target
model, manager, HTTP routes). New shared store: `internal/monitoring/control_policy_store.go`
and its `control_policies`/`control_policy_requests` tables. New shared
contract: `contracts.ControlPolicy` (the "ControlPolicy" family named in
PLAN.md section 13's minimum data model — designed to be reused by package 09
Bandwidth Controls, not CPU-specific). `internal/modules/manager.go` gained a
`DeactivateHooks` map so a control module can require its own cleanup before
`Disable` succeeds; `cmd/payesh-server/main.go` registers
`cpucontrol.Manager.RevertAllForServer` under `cpucontrol.ModuleID`.

## Implemented behavior

- **Quota math** (`quota.go`): integer millicores (1000 = 1 core) per
  PLAN.md section 10; `Describe` renders "1.00 core(s) (1000m) — about 25%
  of this 4-vCPU server", the exact worked example from the plan.
  `QuotaMicros`/`MillicoresFromQuota` convert to/from cgroup v2's
  quota/period microsecond pair and round-trip exactly for the tested range.
- **cgroup v2 adapter** (`cgroup.go`, `FSCgroup`): every method operates on
  the real cgroup v2 file format (`cpu.max`, `cgroup.procs`) against an
  injectable root — production uses `/sys/fs/cgroup`
  (`PAYESH_CGROUP_ROOT` overrides it), tests use a temp directory. This
  exercises the real parsing/writing/ownership logic without needing a
  mounted cgroupfs or root; what it cannot prove is that the kernel actually
  enforces a written quota, which needs a disposable Linux host. Every group
  path is required to live under `payesh/`, and every write/remove operation
  first checks a `payesh.owned` marker file this package itself writes when
  it creates a group — a pre-existing directory without that marker (a
  "shared" cgroup Payesh did not create) is refused outright, not adopted.
  `ParentQuota` walks ancestors to detect and report an inherited stricter
  quota rather than silently promising an allowance the kernel would not
  actually grant.
- **Process identity** (`identity.go`): `/proc/<pid>/stat` field 22
  (starttime) read against an injectable root (production `/proc`), correctly
  handling a `comm` field that itself contains spaces/parentheses. A
  process-group `Apply` re-verifies this before writing anything; a PID whose
  start time no longer matches (reused by an unrelated later process, or the
  original process has exited) is rejected, never silently re-targeted.
  `pidfd_open`-based identity (a stronger, Linux-syscall-only mechanism) is
  documented as a follow-up real-Linux enhancement, not implemented — a plain
  `/proc` read is the portable mechanism this checkpoint can build and test.
- **Manager** (`manager.go`): `Preview` (current effective quota, proposed
  value, parent-stricter warning, human description) → `Apply` (validate →
  require a dedicated group → verify process identity for a process-group
  target → write quota → read back and confirm it matches exactly → persist)
  → `Revert` (restore exactly what the matching `Apply` found beforehand,
  verify, persist). A verification mismatch at any step is durably recorded
  as `failed`, never reported as success. `RevertAllForServer` sweeps every
  currently `applied` CPU policy on a server and is the registered
  `modules.Manager` disable hook.
- **Durable store**: `control_policies` (one row per server/module/target,
  CAS revision via the same `INSERT … ON CONFLICT … DO UPDATE … WHERE
  revision=?` pattern as `module_installations`/`traffic_allowances`) and
  `control_policy_requests` (idempotent preview/apply/revert results).
- **HTTP routes**: `GET /api/v1/servers/{id}/cpu-policies` (list),
  `POST .../cpu-policies/{targetKind}/{targetName}/{preview,apply,revert}`
  with idempotency-key + expected-revision on apply/revert (preview is
  read-only, no idempotency needed). Wired into `internal/fleet/http.go`
  behind the package-04 session/CSRF boundary via `fleet.Options.CPUControlService`.

## Known contract mismatch — needs lead reconciliation

`api/openapi.yaml` (from the package-01 foundation sketch, still only
"ready for review") already contains a *generic* `/servers/{serverId}/policies`
family: `GET`/`POST /policies`, `POST /policies/preview`,
`GET /policies/{policyId}/effective`, `POST /policies/{policyId}/revert` —
addressed by an opaque `policyId` and wrapped in the async `Job` contract
(202 + job status polling). This checkpoint's actual implementation (and,
on inspection, the already-implemented package-06 module lifecycle routes)
instead expose **synchronous**, target-addressed REST endpoints with
idempotency-key + expected-revision CAS, returning the resulting
`ControlPolicy`/`ModuleInstallation` directly — the same pattern package 05's
`POST /servers/{id}/traffic` already established, whose own handoff noted
"later job adapters may wrap it in the package-04 job contract." I did not
rewrite the working, tested implementation to match the older sketch, and did
not edit `openapi.yaml` to describe routes that do not yet match any
document (that would just add a second, equally unreconciled guess).
**This is an explicit, reported conflict, not a silent choice**: the lead
should decide whether to update `openapi.yaml` to describe the actual
synchronous per-target contract (my recommendation, since it is simpler,
already implemented twice, and matches how these actions are genuinely
consumed — an apply either succeeds or fails within the request), or to
migrate modules/traffic/cpu-controls to the generic async `policyId`/`Job`
shape, before any of these packages are accepted. `make contract-check`
still passes because it only checks for required top-level paths/security
metadata, not response-shape agreement with server code.

All pass, including the new `internal/cpucontrol` suite (31 tests): quota
round-trip/description math; cgroup file-format read/write, ownership-marker
creation and shared-directory refusal, parent-quota detection, empty/non-empty
group removal; `/proc/<pid>/stat` parsing including a comm field with spaces
and parentheses, PID-reuse and exited-process detection; the full
manager preview → apply → verify → revert cycle, first-apply-revert removing
the limit entirely, shared-foreign-group refusal recorded as a durable
`failed` policy, stale-PID apply rejection, stale-revision-CAS rejection, and
the `RevertAllForServer` sweep; plus HTTP-level idempotent replay, the
process-group-requires-PID check, revision-conflict-as-409, and unknown-route
404s. `internal/modules` gained a test for the new `DeactivateHooks`
mechanism (hook runs before disable, a failing hook blocks disable and
leaves the module enabled, a succeeding hook allows it to proceed).

## Costs, limitations, and next inputs

Unrun/unmeasured, honestly: real CPU-load enforcement on disposable Linux
(the actual acceptance gate for this package); shared-group refusal,
parent-quota inheritance, PID reuse/exit, restart, and OpenRC-specific
service arrangements against a real init system; `pidfd`-based identity;
`payesh run` (the local CLI workflow to start an unmanaged workload in its
own dedicated group) — not implemented in this checkpoint, left as a
follow-up since it is CLI plumbing rather than the safety-critical
verify/apply/revert core this pass focused on; target *discovery* (listing
existing systemd/OpenRC services for an owner to pick from) — this
checkpoint requires the caller to name a target explicitly rather than
enumerating the host's services, since no systemd/D-Bus integration exists
anywhere in this codebase yet; and the OpenAPI contract mismatch described
above. `cpucontrol.Manager.FS` defaults to nothing (must be supplied) and
`cmd/payesh-server/main.go` points it at `/sys/fs/cgroup`, which does not
exist as a real cgroupfs on this development host — the routes and manager
logic are exercised by tests against a temp-directory stand-in, not a real
mount.

Package 09 (Bandwidth Controls) can reuse `contracts.ControlPolicy`, the
`control_policies`/`control_policy_requests` store, and the
`INSERT … ON CONFLICT … DO UPDATE … WHERE revision=?` CAS pattern without
re-deriving them — only a new `Kind`/parameters payload and its own
FS/tc/nftables adapter are needed. The `modules.Manager.DeactivateHooks`
mechanism is also ready for Bandwidth Controls to register its own cleanup.
