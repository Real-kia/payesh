# Package 08 handoff — CPU Controls

Status: Checkpoint A plus read-only service target discovery and the local
`payesh run` workflow implemented; package 08 is not accepted. No real
CPU-load test has passed. The rebuilt Ubuntu 22.04.1 acceptance host
advertises/delegates the cgroup-v2 CPU controller, but its hierarchy removes
the transient test directory before `cpu.max` is available; the runner reports
this as unsupported and leaves the host unchanged.

## Baseline and files

Builds on package-06's module framework (`modules.Manager.DeactivateHooks`)
and the package-05/06 SQLite store. New package: `internal/cpucontrol/`
(quota math, cgroup v2 file adapter, process-identity verification, target
model, manager, HTTP routes). New shared store: `internal/monitoring/control_policy_store.go`
and its `control_policies`/`control_policy_requests` tables. New shared
contract: `contracts.ControlPolicy` (the "ControlPolicy" family named in
PLAN.md section 13's minimum data model — designed to be reused by package 09
Bandwidth Controls, not CPU-specific). `internal/modules/manager.go` gained a
`DeactivateHooks` map so a control module can require its own cleanup before
`Disable` succeeds; `cmd/payesh-server/main.go` registers
`cpucontrol.Manager.RevertAllForServer` under `cpucontrol.ModuleID`.

## Implemented behavior

- **Quota math** (`quota.go`): integer millicores (1000 = 1 core) per
  PLAN.md section 10; `Describe` renders "1.00 core(s) (1000m) — about 25%
  of this 4-vCPU server", the exact worked example from the plan.
  `QuotaMicros`/`MillicoresFromQuota` convert to/from cgroup v2's
  quota/period microsecond pair and round-trip exactly for the tested range.
- **cgroup v2 adapter** (`cgroup.go`, `FSCgroup`): every method operates on
  the real cgroup v2 file format (`cpu.max`, `cgroup.procs`) against an
  injectable root; tests use a temp directory. The base server intentionally
  does not link this optional implementation until the privileged executor is
  available. Tests exercise the real parsing/writing/ownership logic without needing a
  mounted cgroupfs or root; what it cannot prove is that the kernel actually
  enforces a written quota, which needs a disposable Linux host. Every group
  path is required to live under `payesh/`, and every write/remove operation
  first checks ownership metadata recorded in ordinary durable storage outside
  cgroupfs — a
  pre-existing directory without that record (a
  "shared" cgroup Payesh did not create) is refused outright, not adopted.
  `ParentQuota` walks ancestors to detect and report an inherited stricter
  quota rather than silently promising an allowance the kernel would not
  actually grant.
- **Process identity** (`identity.go`): `/proc/<pid>/stat` field 22
  (starttime) read against an injectable root (production `/proc`), correctly
  handling a `comm` field that itself contains spaces/parentheses. A
  process-group `Apply` requires the process to already be a member of its
  dedicated group and re-verifies identity before writing anything; a PID whose
  start time no longer matches (reused by an unrelated later process, or the
  original process has exited) is rejected, never silently re-targeted.
  `pidfd_open`-based identity (a stronger, Linux-syscall-only mechanism) is
  documented as a follow-up real-Linux enhancement, not implemented — a plain
  `/proc` read is the portable mechanism this checkpoint can build and test.
- **Manager** (`manager.go`): `Preview` (current effective quota, proposed
  value, parent-stricter warning, human description) → `Apply` (validate →
  require a dedicated group → verify process identity for a process-group
  target → write quota → read back and confirm it matches exactly → persist)
  → `Revert` (restore the original pre-Payesh baseline across repeated edits,
  verify, persist). External quota drift is refused rather than overwritten.
  A verification mismatch at any step is durably recorded
  as `failed`, never reported as success. `RevertAllForServer` sweeps every
  currently `applied` CPU policy on a server and is the registered
  `modules.Manager` disable hook when the future module host wires both
  managers through their shared lifecycle lock.
- **Durable store**: `control_policies` (one row per server/module/target,
  CAS revision via the same `INSERT … ON CONFLICT … DO UPDATE … WHERE
  revision=?` pattern as `module_installations`/`traffic_allowances`) and
  `control_policy_requests` (idempotent preview/apply/revert results).
- **HTTP adapter**: `GET /api/v1/servers/{id}/cpu-policies` (list),
  `POST .../cpu-policies/{targetKind}/{targetName}/{preview,apply,revert}`
  with idempotency-key + expected-revision on apply/revert (preview is
  read-only, no idempotency needed). The base server supplies an authenticated
  503 placeholder via `fleet.Options.CPUControlService`; the real adapter is
  not linked into the base artifact.
- **Service target discovery** (`internal/cpucontrol/discovery.go`): the
  read-only adapter first queries systemd with `systemctl list-units
  --type=service --all` and falls back to OpenRC's `rc-status` or `rc-update`.
  Results are sorted and deduplicated into explicit service targets with
  advisory supervisor/active-state metadata. Missing or unsupported init
  tooling returns a typed unsupported-capability error; discovery never
  changes supervisor state and does not imply that a target is safely
  enforceable until the privileged adapter validates it.
- **Linux acceptance harness** (`internal/cpucontrol/linux_acceptance_test.go`):
  the opt-in `TestLinuxCPUControlAcceptance` creates a uniquely named
  Payesh-owned cgroup below `/sys/fs/cgroup`, starts a bounded busy workload,
  attaches it, writes and reads back a 200m quota, and checks `cpu.stat`
  usage stays within a bounded budget before removing the empty group. The
  same probe first verifies that an unmarked foreign group is refused and
  reconstructs the adapter against its ownership directory to cover restart
  recovery. It skips safely when root, cgroup-v2 CPU delegation, or writable
  cgroupfs is unavailable. `scripts/linux-acceptance.sh` now cross-compiles
  and uploads this probe; the remote runner reports `cpu_control=PASS`,
  `UNSUPPORTED`, or `FAIL` without touching an unrelated cgroup.

## OpenAPI contract mismatch — reconciled

`api/openapi.yaml` (from the package-01 foundation sketch) originally
described a *generic* `/servers/{serverId}/policies` family addressed by an
opaque `policyId` and wrapped in the async `Job` contract (202 + job
polling), which didn't match this checkpoint's actual synchronous,
idempotency-keyed, target-addressed implementation (nor the already-shipped
package-06 module routes). This has now been reconciled in favor of what is
actually implemented, rather than rewriting the tested code to match the
older sketch:

- `/servers/{serverId}/modules/{moduleId}/install` was added (it did not
  exist before; the sketch's `POST /servers/{serverId}/modules` did not
  match any real route) with a new `ModuleInstallRequest` schema carrying
  `manifest`/`manifest_signature_b64`/`archive_base64` plus
  `idempotency_key`/`expected_revision`, and a new `ModuleManifest` schema.
  `enable`/`disable`/`remove` now return `200` + `ModuleInstallation`
  directly instead of `202` + `Job`.
- `Module` (catalog entry) and `ModuleInstallation` schemas now match
  `contracts.ModuleCatalogEntry`/`contracts.ModuleInstallation` exactly
  (`server_id`, `revision`, `updated_at`, `error` were missing before).
- The generic `/servers/{serverId}/policies*` family was replaced with the
  actual `/servers/{serverId}/cpu-policies` (list) and
  `/servers/{serverId}/cpu-policies/{targetKind}/{targetName}/{preview,apply,revert}`
  routes, with new `TargetKind`/`TargetName` path parameters and
  `CPUPolicyPreviewRequest`/`CPUPolicyPreview`/`CPUPolicyApplyRequest`/`CPUPolicyRevertRequest`
  schemas. `Policy` now matches `contracts.ControlPolicy` exactly and is
  still reusable by package 09 without another rename.
- `scripts/contract-check.mjs`'s `requiredPaths` was updated to the new path
  names so the check keeps meaning something (required session/CSRF
  metadata on the actual routes) rather than merely passing on unrelated
  strings.

Verified: `make contract-check` passes, the document still parses, and no
`$ref` is left dangling (checked all schema references resolve). This was a
documentation-only change; no Go code changed as part of the reconciliation.

## Costs, limitations, and next inputs

Unrun/unmeasured, honestly: supervisor-owned persistent service placement,
shared-group refusal,
parent-quota inheritance, PID reuse/exit, restart, and OpenRC-specific
service arrangements against a real init system; `pidfd`-based identity;
`payesh run` now starts a command without a shell, creates a Payesh-owned
  dedicated cgroup, attaches the process, optionally writes a quota, and
  removes only an empty owned group. It fails explicitly on non-Linux hosts,
  missing cgroup v2 permissions, invalid paths, process-start/attach errors,
  and unsafe ownership states. Target *discovery* (listing
  existing systemd/OpenRC services for an owner to pick from) is now
  implemented as a read-only command adapter, but remains unconnected to the
  base HTTP service until the authenticated module host exists. It does not
  provide supervisor mutation or claim target ownership. (The OpenAPI contract
  mismatch noted above has already been reconciled in this same pass — see the
  section above.)
The new `payesh-cpu-module` supplies the privileged runtime: real cgroup-v2
hierarchy preparation, the manager/API over a permission-controlled Unix socket,
optional shared-secret authentication, server proxy support, and systemd/OpenRC
definitions. Production routes still return 503 unless the optional socket is
configured. Manager/runtime logic is covered locally and real-mount process
quota enforcement now passes; supervisor-owned service placement remains.

Package 09 (Bandwidth Controls) can reuse `contracts.ControlPolicy`, the
`control_policies`/`control_policy_requests` store, and the
`INSERT … ON CONFLICT … DO UPDATE … WHERE revision=?` CAS pattern without
re-deriving them — only a new `Kind`/parameters payload and its own
FS/tc/nftables adapter are needed. The `modules.Manager.DeactivateHooks`
mechanism is also ready for Bandwidth Controls to register its own cleanup.
