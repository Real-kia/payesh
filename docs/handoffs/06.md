# Package 06 handoff — signed optional-module framework

Status: Checkpoint A implemented; package 06 is not accepted. This checkpoint
does not claim a real payesh-privd wiring, kernel teardown, or provider
release-signing key provisioning.

## Baseline and files

The implementation builds on the package-01 contracts, package-04 fleet/auth
boundary, and the package-03/05 SQLite store. New package seams are
`internal/trust/` (JCS canonicalization and Ed25519 manifest verification),
`internal/modules/` (catalog, eligibility, archive staging, lifecycle state
machine, manager, HTTP routes), and `internal/monitoring/modules_store.go`
(durable per-server module lifecycle rows and idempotent-request records).
Shared wire records live in `internal/contracts/contracts.go`
(`ModuleManifest`, `ModuleCatalogEntry`, `ModuleInstallation`, `ModuleState`);
the server wires the module service from `cmd/payesh-server/main.go` through
`internal/fleet/http.go`.

This handoff also fixed two build-breaking regressions found in the existing
tree before any package-06 code was added (`internal/monitoring/store.go`:
two `*time.Time` dereferences and a stale `RollupPage{}` return left over
from an earlier edit) and two `gofmt` drifts in `contracts.go`/`engine.go`.
`go build ./...` did not compile before these fixes.

## Implemented behavior

- `internal/trust`: an RFC 8785-subset JSON canonicalizer scoped to the shapes
  Payesh manifests actually use (strings, decimal-string integers, RFC 3339
  timestamps, bools, nested objects/arrays — no raw JSON numbers, which are
  rejected outright rather than risking an ECMA-262 formatting interop bug).
  Ed25519 detached-signature verification follows
  `docs/contracts/RELEASE_FORMAT.md` exactly: unpadded base64url signature,
  unknown/expired/revoked key rejection, malformed-signature rejection.
- `internal/modules` catalog: the curated, hardcoded list of the three
  official v1 modules (`port-traffic`, `cpu-controls`, `bandwidth-controls`).
  `bandwidth-controls` declares `traffic-accounting` as a core dependency
  instead of bundling another module. `CheckEligibility` compares a server's
  platform/architecture/capabilities against a manifest and catalog entry and
  reports the exact missing item(s), never a bare "ineligible".
  `ResourceEstimateSource` is explicitly `"unmeasured"` for all three entries
  — no invented benchmark numbers.
- Archive staging (`archive.go`): verifies declared compressed size and
  SHA-256 before opening the archive at all; extracts under a fresh scratch
  directory with per-entry validation (absolute paths, `..` traversal, and
  *every* symlink/hardlink entry rejected outright, entry-count and
  cumulative-unpacked-bytes bounds); a rejected archive leaves no partial
  staging directory. `ActivateAtomic` renames the staged directory into place,
  keeping the previous release as a `.previous` sibling until the caller
  confirms success — matching the release-update rollback contract.
- Lifecycle (`lifecycle.go`): an explicit `(state, event) → state` table
  encoding "install is kept separate from activation" (a completed install
  always lands on `installed-disabled`, never `enabled`), "a failed update
  preserves the previous working state" (`update_failed` returns to whatever
  state `update_start` began from), and "remove requires disable first"
  (`remove_start` is not a legal transition from `enabled`). Illegal
  transitions are rejected, not best-effort guessed.
- `Manager.Install` runs eligibility → durable `downloading` → durable
  `verifying` → signature/checksum verification → durable `installing` →
  staging → atomic activation → bounded health check (`DefaultHealthCheckTimeout`
  = 10s) → durable `installed-disabled`, persisting a state transition at each
  stage so an interruption is always observable as a specific failed step. A
  failed health check rolls the filesystem back to the previous release (or
  removes the new one if there was none) before recording `failed`.
  `Enable`/`Disable`/`Remove` are durable CAS transitions on top of the same
  table; `Remove` deletes the active/staged directories and fails closed
  (state `failed`, files left in place) if that deletion errors, so a failed
  cleanup never deletes the only recoverable copy.
- `internal/monitoring/modules_store.go`: `module_installations` (per-server
  lifecycle row with a compare-and-swap `revision`) and
  `module_lifecycle_requests` (idempotent install/enable/disable/remove
  results, mirroring `traffic_allowance_requests`). The CAS update is one
  SQLite `INSERT … ON CONFLICT … DO UPDATE … WHERE revision=?` statement, so
  "create the first row" and "advance an existing row" share one atomic path
  with no separate read-then-write race window.
- HTTP routes (`internal/modules/http.go`): `GET /api/v1/modules` (catalog),
  `GET /api/v1/servers/{id}/modules` (status), and
  `POST /api/v1/servers/{id}/modules/{moduleId}/{install,enable,disable,remove}`
  with idempotency-key + expected-revision semantics identical in shape to
  the package-05 traffic-configuration endpoint. Wired into
  `internal/fleet/http.go` behind the same browser session/CSRF boundary as
  alerts/traffic when `fleet.Options.ModuleService` is supplied.
- `cmd/payesh-server/main.go` wires a real `modules.Service` whenever
  browser-session mode is enabled. The trust registry is built from
  `PAYESH_MODULE_TRUST_KEY_ID`/`PAYESH_MODULE_TRUST_PUBLIC_KEY_B64`; with
  neither set it is intentionally empty — catalog/status routes keep working,
  and every install request fails closed with "unknown signing key" rather
  than silently trusting an unpinned key. `PAYESH_MODULE_ROOT` overrides the
  default `/var/lib/payesh/modules` staging root.

## OpenAPI contract mismatch — reconciled

Noticed while implementing package 08, and now fixed (see
`docs/handoffs/08.md` for the full change list): `api/openapi.yaml`'s module
paths (from the package-01 foundation sketch) wrapped
install/enable/disable/remove in the async `Job` contract (`202` +
job-status polling), and had no `install` path matching this package's real
route at all. `api/openapi.yaml` now describes the actual synchronous
implementation — `POST /servers/{serverId}/modules/{moduleId}/install`
(new), and `enable`/`disable`/`remove` returning `200` + `ModuleInstallation`
directly with idempotency-key + expected-revision CAS, matching package 05's
traffic endpoint. `Module`/`ModuleInstallation` schemas were also corrected
to match `contracts.ModuleCatalogEntry`/`contracts.ModuleInstallation`.

## Costs, limitations, and next inputs

No real Linux archive extracted from an actual official module release was
tested — every test archive is a synthetic fixture built in-process. No
production release-signing key exists yet (per `docs/contracts/RELEASE_FORMAT.md`,
signing keys are deliberately kept out of this repository); the server's
trust registry is empty by default and installs fail closed until an
operator provisions a real anchor. `payesh-privd` is still an unimplemented
stub (`cmd/payesh-privd/main.go`), so `Enable`/`Disable` only flip the durable
state today — they do not yet start/stop any real userspace process or tear
down kernel rules, and `HealthCheck` defaults to a no-op success unless a
caller injects a real check. Redacted structured audit-event persistence
(`contracts.AuditEvent`) does not exist anywhere in the store yet for any
package; module lifecycle changes are not currently audit-logged. Update
(`update_start`/`update_ok`/`update_failed`) is modeled and tested in the
lifecycle table but has no `Manager` entry point yet — version-comparison and
in-place-upgrade policy is left for a follow-up rather than guessed at here.
`archive.MaxArchiveEntries` (4096) is a conservative bound, not a measured
one.

Packages 07–09 (Port Traffic, CPU Controls, Bandwidth Controls) can build on
`modules.Manager`, `modules.Catalog`, and the `contracts.ModuleInstallation`
lifecycle without re-deriving trust verification or archive safety. The next
integration step should: wire real `payesh-privd` `module.invoke` actions for
enable/disable/health-check, add a real release-signing key provisioning
story, add durable audit events for lifecycle transitions, and exercise
signed archives built from real module release artifacts on disposable Linux
hosts rather than only in-process fixtures.
