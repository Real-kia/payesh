# Package 05 handoff — traffic allowances, alerts, and incidents

Status: Checkpoint A implemented; package 05 is not accepted. This checkpoint
does not claim provider-authoritative billing, external outage observation, or
any resource-control policy.

## Baseline and files

The implementation builds on the package-03 SQLite store and package-04
authenticated fleet boundary. New package seams are `internal/traffic/`,
`internal/alerts/`, and the package-05 durable adapters in
`internal/monitoring/alerts_store.go`. Shared wire records and validation live
in `internal/contracts/contracts.go`; the server wires alert and traffic
services from `cmd/payesh-server/main.go` through `internal/fleet/http.go`.

## Implemented behavior

- Allowances select named interfaces, inbound/outbound/combined direction,
  unsigned byte limits, reset day, billing timezone, and ordered warning
  percentages (default 80/90/100). Calendar boundaries are explicit in the
  selected timezone; reset days 29–31 clamp to the month's final day and DST
  changes are retained as real UTC durations.
- `traffic_periods` remains the durable identity for usage, independent of
  process/reboot state. Size changes apply to the active period. A reset-day,
  timezone, or interface schedule edit records a durable transition at the
  current period's end; a restart cannot apply it early. An owner may explicitly
  start a new period. Complete counter intervals are split transactionally at
  calendar/DST boundaries and explicit owner-started period cutovers, with
  exact integer allocation and no overlapping synthetic identity. Traffic POST
  requests use a durable idempotency record and expected server revision; retries
  return the original result and conflicting reuse is rejected.
- Counter deltas honor the selected interface/direction, preserve uint64
  precision, and return `uncertain` on epoch changes, resets, missing validity,
  overflow, duplicate/out-of-order sequences, or non-monotonic observations.
  Explicitly selected interfaces remain emitted after the bounded display list
  is full; the display cap does not silently disable configured billing.
  Forecasts first inspect a minimum 24-hour window and fall back to a bounded
  seven-day window for sparse streams. They require at least 24 hours of usable
  data, 80% interval coverage, and no counter interval longer than one day.
  Explicit future `as_of` values are rejected; historical active-period totals
  require a contiguous period-boundary replay. Poor or reset data hides the
  estimate rather than manufacturing zero traffic. A target period whose
  durable continuity is not `complete` remains unforecastable even after later
  clean observations, because its counted-byte baseline cannot be reconstructed.
- Generic starter rules cover CPU, available-memory pressure, disk capacity,
  inodes, and unreachable nodes. Traffic starters are installed only from a
  concrete allowance so they carry scope/direction identity; legacy generic
  traffic starters are disabled as superseded. Rules are editable, durable,
  enabled by default, and evaluated from observation timestamps and explicit
  coverage. Each rule has a durable `effective_at` policy boundary advanced by
  material edits and re-enables, preventing queued older observations from
  seeding state. State transitions are pending/firing/recovered with configurable
  duration, recovery hysteresis, hourly-bounded reminders, duplicate-safe event
  IDs, out-of-order rejection, and sparse-sampling precision warnings.
- Maintenance windows suppress delivery without stopping collection. A known
  disconnected/revoked node suppresses secondary metric notifications so an
  outage is grouped rather than producing a notification storm. Incidents share
  a server/group identity, retain at most 200 events and bounded evidence (with
  an explicit truncation marker when needed), and recover with a separate
  transition event. Suppressed reminders retain a durable cadence timestamp,
  so suppression does not create an unbounded history stream and the first
  unsuppressed observation can notify promptly; the node-unreachable rule is
  not itself outage-suppressed.
- Telegram and HTTPS webhook delivery is owner-configured, rejects cleartext
  URLs/credentials/fragments, signs webhook bodies with HMAC when configured,
  caps request/response bodies, retries at most five times with bounded backoff,
  and uses a 128-entry asynchronous queue. Secrets are not serialized. The
  server/CLI accept explicit `PAYESH_ALERT_WEBHOOK_*` and
  `PAYESH_ALERT_TELEGRAM_*` environment configuration and keep credentials in
  memory only. A firing/reminder cadence is committed only after a worker
  successfully delivers to at least one configured destination; queue
  admission or terminal provider failures remain retryable and emit bounded,
  secret-free diagnostics. Durable rule creation/reconciliation rejects more
  than 20,000 total or 4,096 per-server rows, counting disabled rules as well.
- Browser routes expose bounded rule/state/history/maintenance/incident reads,
  idempotent rule/window creation, and traffic allowance configuration plus
  period reads. All package-05 routes inherit package-04 session/CSRF policy in
  the production browser server.

## Contracts consumed or changed

- Added `TrafficAllowance`, `TrafficObservation`, `TrafficForecast`, alert,
  maintenance, and incident records to `contracts`; all byte/revision fields
  retain decimal-string JSON encoding.
- Added `traffic_allowances`, durable schedule-transition/request tables,
  `traffic_usage_ledger`, `post_process_queue`, `collector_epoch_metadata`,
  bounded `collector_epoch_retirements` plus its singleton authority,
  `alert_rules`, `alert_states`, `alert_history`, `maintenance_windows`, and
  `incidents` to the forward-only SQLite migration. `traffic_periods` gained a
  durable `interfaces_json` policy snapshot; `alert_rules` gained
  `effective_at`; alert-state migration adds the durable suppression timestamp.
- Added `/servers/{serverId}/traffic` configuration fields and the package-05
  alert/maintenance/incident semantics to `api/openapi.yaml` and the contract
  docs. The traffic endpoint returns a synchronous durable configuration result
  including the advanced server configuration revision; later job adapters may
  wrap it in the package-04 job contract.
- Durable ingestion now exposes newly accepted samples to the package-05
  processor through `Store.SetIngestionObserver`; both `payesh-server` and
  `payesh ingest` use that post-commit seam. Transport hubs may additionally
  attach an observer through `Hub.SetIngestionObserver`; callback failures do
  not request a resend of samples that are already durable. Accepted samples
  remain in a bounded durable post-process queue until derived work is
  acknowledged, and coverage-gap-only commits wake queued samples that the
  gap makes processable. Traffic charging uses a durable
  server/epoch/sequence/allowance ledger, while processing requires a
  sequence frontier from zero or explicit coverage gaps before mutating alert
  or usage state. Concurrent observer drains and alert state transitions are
  serialized. Exact retired-epoch identities are permanent but bounded by the
  metadata authority limit. At capacity, already-known streams continue while
  unseen opaque epochs fail closed with an explicit pressure error; increasing
  `MetadataMaxRows` on a later prune raises that authority limit. Traffic
  periods are retained while a server has queued derived work so delayed usage
  cannot be relabelled with current allowance configuration. A fresh collector
  epoch's sequence-zero baseline is marked `uncertain` when prior epoch
  metadata exists, and explicit owner-started periods close active predecessors
  transactionally. Forecast reads keep a bounded newest tail and include a
  bounded predecessor interval for ordinary 5s/10s collection edges.

## Costs, limitations, and next inputs

No Linux kernel traffic-classification, provider-billing comparison, external
observer, Telegram endpoint, disposable-fleet, or 24-hour storage soak was run
on this macOS host. Traffic is explicitly a host-side estimate; incoming bytes
may have been billed before Linux drops them. A standalone server cannot prove
its own complete power/network outage. Incident evidence is observational and
bounded, not a forensic archive. The package-03 snapshot/log sources are
bounded adapters; external outage observation and real provider/log
integrations remain the next integration seam.

Package 09 may consume `traffic.Manager`, `TrafficPeriod`, and forecast
continuity without treating a threshold as authorization to throttle or block.
The next integration should connect real metric/log snapshots and an external
observer, preserve the durable idempotency/revision boundaries, and exercise
the notification adapters in a controlled environment.
